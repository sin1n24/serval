# serval「勝率評価バー(WinMeter)」機能追加 実装指示書

## 目的

トーナメント管理システムservalに、進行中の試合の優勢を将棋の評価値バーのように表示する
「WinMeter」機能を追加する。赤コーナー55% / 青コーナー45%のように合計100%で表示し、
試合中のイベント(ダウン、1本、時間経過)に応じてリアルタイムに変動する。
初心者の観戦補助・会場と配信の盛り上げが目的で、精度より「もっともらしく動く」ことを優先する。

## 前提: かわロボのルール要点

- 1ラウンド2分。予選は1ラウンド(1本先取)、決勝は最大3ラウンド(2本先取)+延長1ラウンド。
- 「1本」の条件: 場外、ダウン後の10カウント、反則・戦意なし・ギブアップ等。
- ダウン: 審判が宣言し1からカウント、10カウント(「9、それまで」)で相手に1本。復帰でカウントリセット。
- ラウンド時間切れは引き分け。全ラウンド引き分け等で勝敗が決まらない場合は判定(実態はほぼコイントス=50%)。

## アーキテクチャ方針

- **事前レーティングはオフライン計算**。別途Pythonツール(build_ratings.py)が過去大会の
  servalエクスポートJSONから `ratings.json` を生成する。servalはこれをインポートして使う。
  serval側でレーティングの「学習」はしない。推論とライブ更新のみ。
- 評価バー画面は**既存の別画面配信の仕組み(別画1〜3と同様)に「別画4: WinMeter」として追加**する。
- 操作は既存の管理画面に最小限のボタンを追加する(下記UI仕様)。
- GAS経由のポーリング遅延は数秒まで許容。表示側はローカルで1秒ごとに補間更新する
  (カウントや残り時間の進行はクライアント側の時計で進め、サーバー状態で補正)。

## 最初にやること: コード調査

実装前に以下を調査し、統合ポイントと実装計画を報告すること。

1. 「この試合を次の試合にする」で設定される現在試合の状態(spotlight等)がどこに保持され、
   別画面へどう配信されているか。
2. 本数別タイマー(1本目/2本目/3本目、02:00カウントダウン)の開始/停止/残り時間の状態管理。
   タイマー停止(試合中止)がどう表現されるか。
3. 勝ち方ボタン(1-0/1-1/2-0/2-1/不戦勝/勝者なし)押下時のデータフロー。
   試合の途中で本数(スコア)を保持する仕組みがあるか、無ければどこに足すべきか。
4. 別画1〜3がどうやって状態を受信・描画しているか(ポーリング周期、データ形式)。
5. 保存ファイル(エクスポートJSON)のスキーマに新フィールドを追加する際の互換性の作法。

## データ仕様(検証済み)

servalエクスポートJSONについて以下は実データで確認済み。前提としてよい。

- `tournaments[].results["r-j"].win`: 0 = 上側スロット(赤)の勝ち、1 = 下側スロット(青)の勝ち。
- `games[].elapsed`: 2:00カウントダウンの残り時間表示。ラウンド実時間 = 120 − elapsed。
- `roster[].representative`: 同一人物の複数ロボットをグルーピングする文字。ただし大会横断で
  一意ではないため、ratings.jsonは当面ロボット名(playerName)をキーとする。

### ratings.json の形式

```json
{
  "generated": "2026-07-12T11:46:35",
  "key_field": "name",
  "lambda": 0.0544,
  "entities": {
    "ハイランドタージver.5": {"elo": 1581.5, "rounds": 13},
    "宙": {"elo": 1572.6, "rounds": 10}
  },
  "h2h": [
    {"a": "宙", "b": "狐", "pts_a": 2, "pts_b": 1}
  ]
}
```

- `lambda`: 1秒あたりの「1本」発生率(両者合計)の全体平均。
- `entities`: ロボット名 → Elo。未登録のロボットは Elo 1500 として扱う。
- `h2h`: 直接対決の取得本数。

## 評価エンジン仕様(JSモジュール、純関数で実装しテスト可能に)

参照実装として `engine.py`(Python)を同梱する。以下はその要点。数式はこの通りに実装すること。

### 1. 事前の奪取シェア share(Aが次の1本を取る側である確率)

```
eloLogit = (eloA - eloB) / 400 * ln(10)
h2hLogit = ln((ptsA + 2) / (ptsB + 2))        // 仮想2本ずつで平滑化
logit0   = 0.7 * eloLogit + 0.3 * h2hLogit
share    = sigmoid(logit0)
```

### 2. ラウンドの結果確率(残り時間 t 秒)

```
pDecide = 1 - exp(-lambda * t)
qA = share_live * pDecide,  qB = (1-share_live) * pDecide,  qDraw = 1 - pDecide
```

### 3. 試合勝率

- 予選(1本先取): `P(A) = qA + 0.5 * qDraw`
- 決勝(2本先取): 現在スコア(a,b)と残りラウンド数(最大3+延長1)で再帰計算。
  engine.py の `match_win_prob()` をそのまま移植する。引き分けラウンドは本数に数えず、
  全ラウンド消化で未決着なら延長1本勝負、それでも未決着なら0.5(判定)。
- 表示は 5%〜95% にクランプ(0%/100%は出さない)。

### 4. ライブ層(モメンタム)

```
share_live = sigmoid(logit0 + momA - momB)
```

- momX はイベントで加算され、半減期 HALF_LIFE 秒で指数減衰する(毎秒 mom *= 0.5^(1/HALF_LIFE))。
- イベントと加算値(すべて設定オブジェクト PARAMS に集約し調整可能にする):
  - 手動「攻勢」ボタン(任意実装): +MOM_MANUAL (既定 0.4)
  - ダウンから相手が復帰した(=ダウンを奪った実績): 奪った側に +MOM_KNOCKDOWN (既定 0.3、これは減衰半減期を長め60sに)

### 5. ダウンカウントの扱い

側Bがダウン中、カウント n(ダウン宣言時刻からクライアント時計で約1秒/カウント進行、
審判と多少ずれてよい)のとき:

```
pFail = (1 - C_RECOVER)^(10 - n)      // C_RECOVER: 1カウントあたり復帰確率、既定 0.067
P(A) = pFail * P(win | Aに1本追加) + (1 - pFail) * P(win | 継続)
```

- カウント進行に同期してバーがじわじわ動く。復帰したら通常計算に戻り、奪った側にモメンタム加算。
- 両者同時ダウンは各々独立にカウント(ルール準拠)。
- ダウン中に相手が場外→ダウン側に1本、というルールがあるため確率は0に張り付かせない
  (クランプ5%が下限)。

### 6. 時間の扱い

- 残り時間 t は既存の本数別タイマーと連動する。タイマー停止中(試合中止・修理)は
  t を凍結し、モメンタム減衰も停止する。
- ラウンド間(次のタイマー開始前)は t = 120 として計算する。

## UI仕様

### 管理画面への追加(現在試合パネルの下に「WinMeter」セクション)

- 事前勝率と現在勝率のミニバー表示(オペレーター確認用)。
- ボタン: 「赤ダウン」「青ダウン」「復帰」(押した側のカウント開始/リセット)。
- ボタン: 「赤1本」「青1本」(ラウンド決着。スコア更新し、次ラウンドへ。取り方の記録は
  任意: 場外/10カウント/その他 のサブ選択があれば将来のデータ蓄積に使えるが、フェーズ1では省略可)。
- 「取り直し」(モメンタムのみリセット)、「WinMeterリセット」(試合状態全体リセット)。
- ratings.json のインポートUI(ファイル選択)。インポート状態(機体数・生成日時)を表示。
- 試合形式(1本先取/2本先取)の指定。既存に試合形式の概念があればそれに連動、なければ手動トグル。

### 別画4: WinMeter画面(配信・会場向け)

- 横長バー(既存の別画面と同じウィンドウ運用を想定。目安 1920x200 だが既存の作法に合わせる)。
- 左=赤コーナー、右=青コーナー。ロボット名(+操縦者名があれば)表示。
  ※配信でのプライバシー配慮のため、名前の表示/非表示は既存の表示設定に倣いトグル可能にする。
- 中央にパーセント表示。バーは変動時にイージングで滑らかに動く。
- ダウンカウント中はカウント数を大きく表示(観客が一番盛り上がる瞬間)。
- 「1本」確定時は短いアニメーション演出(既存のSE/演出の仕組みがあれば連動)。
- 本数表示(決勝時: ●○ 形式など)。

## パラメータ既定値(PARAMS オブジェクトに集約)

| 名前 | 既定値 | 意味 |
|---|---|---|
| LAMBDA | ratings.jsonから | 1本発生率/秒(フォールバック 1/60) |
| CLAMP | [0.05, 0.95] | 表示勝率の範囲 |
| DRAW_COIN | 0.5 | 判定の勝率 |
| W_H2H | 0.3 | 直接対決項の重み |
| H2H_PRIOR | 2 | h2h平滑化の仮想本数(片側) |
| HALF_LIFE | 8 | モメンタム半減期(秒) |
| MOM_MANUAL | 0.4 | 攻勢ボタンの加算 |
| MOM_KNOCKDOWN | 0.3 | ダウン奪取実績の加算(半減期60s) |
| C_RECOVER | 0.067 | 1カウントあたり復帰確率 |

## 実装ステップ(この順で、各ステップごとに確認を挟む)

1. コード調査レポート(上記5点)と実装計画の提示。
2. 評価エンジンJSモジュール(engine.pyの移植)。純関数+簡単なテスト
   (例: share=0.6, λ=0.0544 で予選の残り3秒勝率が約51.5%になること、
    2本先取で(1,0)スコア時に約84%になること — engine.py実行結果と照合)。
3. ratings.jsonインポートと現在試合との名前マッチング(完全一致、未登録は1500)。
4. 管理画面のWinMeterセクション。
5. 別画4の表示画面と配信連動。
6. 通し動作確認シナリオ: 試合設定→事前勝率表示→タイマー開始→ダウン→カウント進行→
   復帰→1本→(決勝なら)次ラウンド→試合終了、の一連でバーが仕様通り動くこと。

## 制約

- 既存機能を壊さない。保存ファイルの新フィールドはすべてオプショナルにし、
  旧ファイルの読み込み互換を維持する。
- WinMeterの状態は揮発でよい(保存対象は ratings.json のインポート内容と設定のみ)。
- 外部ライブラリ・有料APIは使わない。
- パラメータはすべて PARAMS に集約し、コンソールまたは設定UIから調整できるようにする。
